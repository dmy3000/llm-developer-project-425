# AI-агент службы поддержки

[![hexlet-check](https://github.com/dmy3000/llm-developer-project-425/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/dmy3000/llm-developer-project-425/actions)

Учебный проект: помощник службы поддержки для сотрудников компании на Yandex Cloud.

Планируемый сценарий:

1. Программа получает обращение по email через IMAP.
2. Агент ищет ответ в корпоративной базе знаний с помощью RAG.
3. Если требуется помощь сотрудника поддержки, агент вызывает инструмент создания заявки.
4. Заявки и история переписки сохраняются в YDB, ответы отправляются через SMTP.
5. Отдельный workflow ежедневно отправляет оператору список зависших заявок.

## Текущий статус

Подготовлено облачное окружение и сохранена начальная конфигурация Responses API.
Вручную проверен полный локальный цикл Mail.ru IMAP → Responses API → SMTP:
ответ доставлен, исходное тестовое письмо отмечено прочитанным, повторный поиск
вернул ноль непрочитанных тестовых писем.

Обработчик `handle` развёрнут в закрытой Cloud Function `email-poller`; версия
получила статус `ACTIVE`. Первый ручной вызов из облака завершился с HTTP 200
и `processed: 1`: SMTP принял ответ, исходное письмо отмечено прочитанным.
Доставка этого облачного ответа в ящик получателя подтверждена пользователем.
Создан и проверен таймер `email-poller-timer`: пользователь получил один новый
автоматический ответ. После короткой проверки таймер приостановлен (`PAUSED`).
В YDB `help-desk-db` созданы таблицы `tickets` и `messages`; проверены их столбцы,
первичные ключи и индекс заявок по пользователю. Реализованы функции
`create_ticket` и `list_my_tickets`; проверки без облака проходят. Создание одной
синтетической заявки и чтение через индекс подтверждены в YDB 30 октября 2026 года.
Обработчик заявок развёрнут в закрытой Cloud Function `ydb-tickets`;
создание и чтение через неё проверены. Закрытый шлюз `ydb-tickets-mcp` подключён
в коде вызова агента; модель создала синтетическую заявку и прочитала список.
Сохранение переписки в `messages` и передача истории модели реализованы;
проверены реальные токены, маскирование контактов и связь реплик с тикетом.


Установите [Yandex Cloud CLI](https://yandex.cloud/ru/docs/cli/quickstart) и настройте
отдельный профиль для учебного облака. В текущем окружении используется профиль
`hexlet`. Не изменяйте рабочие профили и не публикуйте токены авторизации.

Для работы с YDB установите SDK в отдельное окружение проекта:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r src/ydb_tickets/requirements.txt
```

Каталог `.venv/` исключён из Git. Системные пакеты Python не изменяются.

Создайте локальный `.env` по образцу `.env.example`. Если файл уже существует,
не перезаписывайте его: проверьте и дополните нужные переменные.

```dotenv
YDB_ENDPOINT_SECRET_ID=
YDB_DATABASE_SECRET_ID=
AGENT_ID=
```

- `YDB_ENDPOINT_SECRET_ID` — ID секрета Lockbox `ydb-endpoint`.
- `YDB_DATABASE_SECRET_ID` — ID секрета Lockbox `ydb-database`.
- `AGENT_ID` — ID сохранённой конфигурации `help-desk` в Responses API.

Это идентификаторы ресурсов, а не значения их содержимого. При заполнении ID секрета
используйте верхнее поле `id` или `current_version.secret_id`, а не ID версии.
Локальный `.env` исключён из Git через `.gitignore`; в `.env.example` идентификаторы
ресурсов и адреса пользователей не заполнены, оставлены только общие настройки.

### База данных

Создана отдельная база YDB Serverless `help-desk-db`; после создания проверен статус
`RUNNING`. В ней созданы и проверены две таблицы:

- `tickets` — заявки: категория, статус, текст, пользователь и даты.
  Первичный ключ — `id`; глобальный индекс `tickets_by_user` по `user_id`.
- `messages` — переписка: роль, текст, связь с заявкой, модель, токены и задержка.
  Первичный ключ — `(user_id, id)`; `ticket_id` может отсутствовать.

Схема находится в [src/ydb_tickets/schema.sql](src/ydb_tickets/schema.sql).
Она содержит только `CREATE TABLE`: выполняйте её при подготовке новой базы,
после проверки отсутствия этих таблиц. Для текущей `help-desk-db` повторно
выполнять её не требуется. Автоматической миграции существующей схемы нет.
При создании таблиц письма и заявки не записывались, данные не удалялись.
База `ydb717` от предыдущей RAG-практики не изменялась.

### Создание и чтение заявок

В `src/ydb_tickets/index.py` добавлена функция
`create_ticket(pool, user_id, category, text)`. Она принимает пул `ydb.SessionPool`,
проверяет обязательные поля, разрешает категории `bug`, `docs`, `feature`, `access`
и записывает заявку со статусом `open` через prepared statement с параметрами.
`user_id` передаёт вызывающий код из идентификатора отправителя, а не из ответа LLM.
Проверка полномочий пользователя должна выполняться при подключении обработчика.

Перед записью в тексте скрываются обычные email и телефоны РФ с префиксом 7/8.
Это ограниченное маскирование: ФИО, адреса, документы, международные телефоны
и другие виды персональных данных не покрываются. `user_id` сохраняется отдельно
для поиска заявок пользователя и не маскируется как текст обращения.

При успешном подтверждении транзакции функция возвращает `ticket_id` и `created_at`
в UTC. Ошибки БД передаются вызывающему коду. UUID и дата сохраняются при повторах
SDK внутри одного вызова; повторный внешний вызов создаёт новую заявку — защиты
по ключу идемпотентности пока нет.

Проверки без доступа к почте, модели и облаку:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

`list_my_tickets(pool, user_id)` читает заявки через индекс `tickets_by_user`
с параметром `$user_id`, сортирует от новых к старым и возвращает список объектов
с полями `id`, `status`, `category`, `text`, `created_at`. Даты представлены строками
UTC в ISO 8601. Для пользователя без заявок возвращается пустой список; ошибки
YDB передаются вызывающему коду. Предел учебной версии — 100 заявок на пользователя:
при превышении возникает явная ошибка, а не обрезанный список. Для больших объёмов
понадобится постраничная выдача. Функция фильтрует по переданному идентификатору;
авторизацию отправителя должен обеспечивать вызывающий код.

### Обработчик `ydb-tickets`

Точка входа `index.handle` поддерживает три формата:

- прямой вызов с `action: create-ticket` или `action: list-my-tickets`;
- аргументы MCP без `action`: `user_id`, `category`, `text` для создания,
  только `user_id` для списка;
- HTTP POST с JSON в `body`, включая `isBase64Encoded: true`.

Пример прямого запроса списка:

```json
{"action": "list-my-tickets", "user_id": "mihey3000@yandex.ru"}
```

Прямой вызов и MCP получают результат как JSON-объект или массив. Для HTTP
добавляется обёртка `statusCode`, `headers`, `body`, `isBase64Encoded`.
Некорректный HTTP-запрос получает 400, неподдерживаемый метод — 405,
чужой пользователь — 403, ошибка подключения или операции — 500.
При прямом вызове ошибки приводят к исключению; ошибка БД не подменяется пустым
списком или сообщением об успешном создании. При неопределённом результате записи
сначала проверьте список заявок: повторное создание может дать дубль.

Это однопользовательский учебный стенд. `TICKETS_USER_ID` задаёт разрешённого
пользователя в конфигурации функции. Переданный `user_id` должен совпадать с ним;
проверка выполняется до подключения к YDB. Такая привязка ограничивает инструмент,
но не заменяет аутентификацию нескольких сотрудников. Для многопользовательского
сервиса потребуется проверенная идентичность из доверенного канала.

`YDB_ENDPOINT` и `YDB_DATABASE` подставляются из Lockbox при запуске версии.
IAM-токен берётся из контекста прикреплённого сервисного аккаунта; статические
ключи в коде не используются. В журнал ошибок попадают только название события
и тип исключения, без писем, аргументов, токенов и диагностического текста SDK.
Текст обращения ограничен 64 КиБ, HTTP-тело — 68 КиБ после декодирования,
JSON-ответ — 1 МиБ; превышение не приводит к незаметному обрезанию.

Для загрузки кода нужен ZIP с двумя файлами в корне: `index.py` и
`requirements.txt` из `src/ydb_tickets/`. `.env`, виртуальное окружение,
тесты и приватные ключи в архив не включаются.

### История переписки и телеметрия

Требования: [шаг 5 проекта](https://ru.hexlet.io/projects/425/members/54401?step=5),
раздел «Задачи», пункт 8 и «Результат шага». В одной подсказке чтение истории
объявлено необязательным; реализация следует явному требованию multi-turn.

`src/message_history.py` работает с уже созданной таблицей `messages`, без
пересоздания схемы. Историю пишет poller напрямую, без MCP и решения модели:

1. Читает последние 10 реплик только текущего `ALLOWED_SENDER` и разворачивает
   их от старых к новым. `agent` передаётся Responses API как `assistant`,
   текущее письмо добавляется последним, отдельно от истории.
2. До обращения к модели сохраняет входящую реплику (`user`, `ticket_id=NULL`).
3. После ответа записывает `agent`: `model` из `AGENT_MODEL`, токены из `usage`,
   `latency_ms` из `time.monotonic()`. Для входящего сообщения счётчики равны 0,
   модель не задана: это сообщение не является ответом LLM.
4. Если `mcp_call name=create-ticket` подтвердил UUID, проверяет принадлежность
   тикета и исходного сообщения пользователю. Ответ и обновление `ticket_id`
   входящей реплики коммитятся одной транзакцией.
5. Только после подтверждения записи передаёт ответ SMTP и отмечает письмо
   прочитанным. Сбой базы, неполная телеметрия или ошибка инструмента прерывают цикл.

Тексты маскируются той же функцией `mask_pii`, что и заявки: обычные email и
телефоны РФ с префиксом 7/8. Это не покрывает все виды PII; `user_id` хранится
отдельно как ключ. Письма, история, токены авторизации и аргументы инструментов
не выводятся в журнал: событие `history_saved` содержит только число прошлых
реплик и признак созданной заявки.

История включается наличием `YDB_ENDPOINT` или `YDB_DATABASE`: обе настройки
обязательны, как и `AGENT_MODEL`. Без настроек YDB остаётся прежний почтовый режим.
`AGENT_MODEL` должен соответствовать модели сохранённой конфигурации `AGENT_ID`.
Для локального режима установите `src/requirements.txt`; URI и путь YDB
передаются через окружение, в облаке — через существующие секреты Lockbox.

В архив почтовой функции входят `email_poller.py`, `message_history.py`,

### Сервисный аккаунт

Создан `ai-studio-sa` — отдельная учётная запись компонентов приложения.
На учебный каталог ему назначены шесть ролей:

- `functions.functionInvoker` — вызов Cloud Functions.
- `serverless.mcpGateways.invoker` — вызов MCP-шлюзов.
- `lockbox.payloadViewer` — чтение содержимого секретов Lockbox.
- `ai.languageModels.user` — обращение к языковым моделям.
- `ai.assistants.editor` — работа с Responses API и управление ресурсами ассистентов.
- `ydb.editor` — работа с YDB, включая данные.

Роли назначены на весь каталог, а не только на ресурсы этого проекта. Существующие
права другого сервисного аккаунта `test-name` сохранены. Ключи для `ai-studio-sa`
не создавались; для Cloud Functions токен прикреплённого сервисного аккаунта
доступен обработчику через `context.token`.

## Ручная проверка промпта

Проверки проводились в Playground без базы знаний и инструментов, с очисткой диалога
между отдельными попытками:

- «Как у нас в компании оформить командировку?» — первая версия инструкции допускала
  выдуманный регламент. После явного запрета использовать собственные знания при
  отсутствии документов модель сообщила, что информации нет.
- «Сломался принтер. Создай заявку и сообщи её номер.» — модель не выдала номер, но
  сначала придумала внутренний портал. После дополнительного запрета придумывать
  каналы обращения в наблюдаемом ответе не было ни номера, ни портала.

Эти наблюдения относятся к конкретным ручным запускам разных версий промпта.
Полный регрессионный прогон финальной версии и автоматические проверки ещё не сделаны.
Температура `0` и инструкции сами по себе не гарантируют достоверность ответов.

## Использование

Почтовая логика находится в `src/email_poller.py`:

- `read_test_messages(password)` — читает подходящие непрочитанные письма без изменения флагов.
- `run_test_cycle(password, iam_token)` — требует ровно одно тестовое письмо,
  получает ответ модели, отправляет его и только затем устанавливает `\Seen`.
- `handle(event, context)` — точка входа для Cloud Functions. Получает IAM-токен
  из `context.token["access_token"]`, пароль — из секретной переменной
  `IMAP_PASSWORD`. Возвращает JSON с числом обработанных писем (`0` или `1`).

Оба режима обрабатывают только точный адрес `ALLOWED_SENDER` и точную тему
`TEST_SUBJECT`. При нескольких подходящих письмах запуск завершается ошибкой
до обращения к модели и отправки ответа. Это ограничение первой учебной проверки.
Остальные письма не отправляются модели. Фильтр по `From` не подтверждает подлинность
отправителя и не заменяет проверку аутентификации почты.

Для облачной версии потребуются обычные переменные из `.env.example` (параметры
YDB для этого этапа не используются), прикреплённый сервисный аккаунт и привязка
Lockbox `email-credentials` / `password` → `IMAP_PASSWORD`. Один пароль используется
для IMAP и SMTP. Если поместить `src/email_poller.py` в корень архива с именем
`email_poller.py`, точка входа версии — `email_poller.handle`.
В архив включайте только этот исходник; `.env` и пароль в архив не входят.

При ошибке модели или SMTP письмо остаётся непрочитанным, ошибка не маскируется.
При успешной отправке и неудачной установке флага повторный запуск может отправить
дубликат. Параллельные запуски также пока не защищены от повторной отправки.
Таймер использовался только для короткой учебной проверки с одним письмом,
затем приостановлен. Перед постоянной работой нужна защита между экземплярами.
